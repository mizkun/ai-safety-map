# マップを軽く保つ

このサイトは記事の読み込みだけでなく、移動・拡大・タップへの応答を扱う。初回転送量、操作処理、描画、再訪時のキャッシュを分けて確認する。

## 実装方針

- 初期表示は要点から始める。全要素は表示範囲を切り替えて開く。PCは画面寸法に合わせ、スマホの最初は8経路の一覧、経路内は読めるカード幅を優先する。ツアーは案内文と対象箇所を同時に表示し、章の関連項目だけを展開する。
- 巨大な要素全体をCSSで拡大縮小しない。描画用のSVGとカードの親要素は、画面と小さい先読み余白の範囲に限る。スクロールの広さだけを確保する空のステージと分ける。
- 画面外のカードは描かない。空白を詰めても、カードの周囲の余白とANDの包含関係は保つ。
- カードは半透明のグラデーション、白い輪郭、短い影でガラスの質感を出し、カードごとの背景ぼかしは使わない。スマホではツールバーとダイアログ背景のぼかしも使わない。
- ポインターのイベントを1フレームに一度へまとめる。ピンチ中に毎回要素位置を読み直さない。サイズが更新された後で指の中心へスクロールする。
- カードの暗黙のポインターキャプチャを移す際のイベントを、指が離れたイベントと混同しない。
- 詳細本文は初めて必要になった時に、選択中の言語だけ取得する。資料パネルのJavaScriptも遅延読み込みする。本文を取得してもマップの配置・表示位置を作り直さない。
- 詳細JSONと静的ファイルは内容に対応するファイル名を使う。同じファイルはブラウザーのキャッシュを利用でき、内容が変わるとURLも変わる。

## PWAとAMPの判断

PWAのキャッシュは再訪とオフラインに有用だが、重い描画を解消する仕組みではない。最初に全データを先読みする実装は避ける。現段階では通常のHTTPキャッシュと版付きファイルを使い、Service Workerは導入しない。オフライン対応を追加する際は、最新HTMLの取得を優先し、保存した内容を表示する場合にその旨と確認日を明示する必要がある。

AMPは独自JavaScriptの量とAPIに制限があり、現在のReact/MUIのマップとピンチ操作をそのまま移せない。今回は採用しない。

## 継続して確かめること

`npm run test:map`で、画面寸法ごとの初期倍率、描画面積の上限、イベントの集約、ポインターキャプチャの移行、カードと線の幾何関係を検査する。表示項目の増加で図が広がる場合も、縮小しすぎて文字を読めなくする設計には戻さない。

静的ファイル量やNode.jsの処理時間は、実機の滑らかさの測定ではない。実機のINP、操作中のフレーム、メモリー、初回・再訪の通信は別の測定として記録する。FPSや改善率をファイル量から推定して報告しない。
